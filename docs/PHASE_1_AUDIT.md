## A. Phase 1 System Overview

The app is an artist-owned, Spanish-first bilingual music site with releases, preview playback, biography media, free email capture/reward delivery, hosted artist support, closed paid Vault products, capability-based private access, permission handling and an inactive email outbox. It has no fan login, artist administration, CMS or fully implemented multi-artist tenant routing.

```mermaid
sequenceDiagram
    participant Fan
    participant SPA as React SPA
    participant Edge as Supabase Edge Functions
    participant DB as PostgreSQL and outbox
    participant Stripe
    participant Storage as Private Storage
    Fan->>SPA: Contact and explicit optional consent
    SPA->>Edge: capture-fan with request ID and locale
    Edge->>DB: Atomic fan/capture/permission/job records
    Edge->>Storage: Sign free reward for 300 seconds
    Edge-->>SPA: Capture capability and optional reward URL
    SPA->>Edge: create-checkout with capability
    Edge->>DB: Persist canonical payment attempt
    Edge->>Stripe: Hosted Checkout at server price
    Stripe-->>Fan: Hosted payment page
    Stripe->>Edge: Signed webhook
    Edge->>Stripe: Retrieve current canonical payment state
    Edge->>DB: Atomic purchase, entitlement, event and job
    SPA->>Edge: checkout-status with scoped capability
    Edge-->>SPA: Verified completion and access capability
    SPA->>Edge: redeem-vault
    Edge->>DB: Recheck purchase and active entitlement
    Edge->>Storage: Sign paid download for 300 seconds
    Edge-->>Fan: Private download link
    Note over DB: Email jobs remain pending; sending is not activated
```

### Actual fan journeys

**Free reward.** Visitor submits a validated email and current UI locale with opt-in false unless explicitly selected. `capture_fan` atomically creates/reuses the normalized fan and records capture/permission request/job. Stay Close and release capture use `source=stay_close`. The server signs the free private object and returns `magnetUrl`; UI shows download only when that URL exists. Download is a five-minute bearer Storage link; expiry denies further use. The queued email can eventually supply a 48-hour reward capability that signs another five-minute URL. Today the browser reward has provider-backed historical evidence; the email portion is unverified and pending.

**Paid item.** Public Vault items all display coming soon. The explicitly invoked, authenticated local operator path can expose only Acción. Contact is captured before an attempt and Stripe Session are created. The fan follows hosted Checkout; browser return starts status polling and cannot authorize payment. A signature-verified event retrieves canonical Stripe state and transactionally commits purchase, unlock, events and confirmation job. Scoped status/access → DB entitlement recheck → signed file allows private download. Recovery requests queue new links only to the stored email; that email step has not been delivered.

**Artist support.** The amount selector offers $5/$15/$30 and custom bounded integer-cent amounts. Capture precedes hosted Checkout; only verified fulfillment completes the attempt and records a tip purchase. It creates a transactional purchase confirmation job, never a Vault unlock. Confirmed/processing/cancelled/failed/expired states come from server status and return context. Cancelling the hosted page is UI context; it does not set a DB `cancelled` status or cancel the resumable Session. The unpaid Session later expires. Actual provider tip payment is not verified.

**Email permission.** Contact storage and requested reward/transactional receipts do not require marketing opt-in. Explicit checkbox → pending record and confirmation link → user presses Confirm → verified/granted consent and one welcome job. Only current verified permission permits welcome/reminder dispatch. Unsubscribe link plus explicit button records revocation; already queued marketing jobs become skipped at the next send-time check. Transactional access stays available. There is a race after permission check and before network acceptance; accepted/in-flight messages cannot be recalled. The full inbox journey remains to be tested.

**Spanish/English.** First visit defaults to Spanish; globe selection persists in localStorage and updates UI, forms, dates and metadata without remounting audio. Forms send current locale for new fans. Repeat capture does not update an existing fan's original preferred language, so changing the browser can diverge from communication locale. Worker templates use stored EN/ES; some generated link labels remain bilingual/English. No explicit locale is sent to hosted Stripe Checkout. Storage-blocked browsers retain choice only in memory.

## C. Stripe Verification Report

### Environment and payment integrity

The connected account is the named **Jona Ferreira sandbox**, `livemode=false`. The local key has a test prefix and its read-only Account lookup matches the intended sandbox. Supabase secret digests match the local `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; values/digests were never printed. The enabled destination targets this project's `stripe-webhook`, with all required events and API version `2026-09-30.endive`. No environment, key or destination was changed.

Hosted Checkout needs no browser Stripe secret or publishable key. Product prices/currency are controlled by shared server catalog; tips are validated integer cents. Session/PaymentIntent metadata identifies attempts/artist and optional operator testing. A stored attempt plus `checkout:<attempt>` provider idempotency and immutable request checks prevent normal duplicate creation. A browser success redirect never writes paid state.

The webhook uses raw body + signing secret and Stripe's timestamp/signature verification, then canonical Session/Charge/PaymentIntent retrieval to tolerate out-of-order events. Four checkout events all use current `payment_status`; only paid state fulfills. Unpaid expired/async-failed sessions update attempt state without overwriting completed attempts. Refund uses current cumulative charge state. Database fulfillment/refund RPCs are service-only, transactional, fan-serialized, price/session/currency checked and protected by unique purchase IDs and event receipts. Non-fulfilling expiry/failure branches do not write `webhook_events` receipts; their state updates are repeatable.

All five required event types are implemented and subscribed: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`. Canonical state retrieval and SQL failure return 503 for provider retry; an out-of-order refund before purchase remains retryable. Full refund is terminal, preserves purchase records and prevents new redemption; another qualifying payment for the same fan/item can preserve entitlement. Issued Storage links retain their remaining five-minute lifetime.
