# Resend readiness and owner setup

Audited October 27, 2026. This is a configuration/implementation plan. No email, worker invocation, scheduler activation or deployment was performed. See [the complete Phase 1 audit](../PHASE_1_AUDIT.md) for Stripe, architecture, repository and test evidence.

## Already implemented

`supabase/functions/_shared/messaging.ts` is a direct HTTP Resend adapter, not an SDK or switchable provider framework. It posts plain-text messages to `/emails`, freezes the complete outgoing body in protected `delivery_jobs.payload.emailBody`, uses the job's stable `dedupe_key` as `Idempotency-Key`, stores the accepted provider ID, and retries failures. `templates.ts` provides five EN/ES variants. There are no HTML/React Email templates and no bulk-send endpoint.

The core migration creates the durable outbox, service-only claim/consent/reminder RPCs, ten-row `SKIP LOCKED` claiming, two-minute leases and six-attempt cap. Purchase fulfillment creates its confirmation job in the payment transaction. Marketing jobs check current verified permission after claiming, even if their bodies were frozen earlier. Email failures do not undo purchases or entitlements.

## Needs configuration

Read-only Supabase secret-digest checks show `EMAIL_PROVIDER_API_KEY`, `EMAIL_FROM_ADDRESS`, `SUPPORT_EMAIL` and `BUSINESS_POSTAL_ADDRESS` are present as **empty** values; local values are empty too. A secret name appearing in the Dashboard does not prove configuration. Resend account/domain status and actual inbox delivery were not verified.

## Needs implementation before automated delivery

1. **Enforce an elapsed retry deadline.** Six attempts bound count, not wall time. `claim_jobs` has no first-send timestamp or 24-hour cutoff. If the worker is paused after an ambiguous send and resumes more than 24 hours later, the same key can be accepted again. Add persisted first-attempt/deadline state and terminal handling outside the safe window; retain frozen bodies/keys and test crash/lease/downtime cases. Resend documents a 24-hour retention window in [Idempotency Keys](https://resend.com/docs/dashboard/emails/idempotency-keys).
2. **Handle old queued links and the existing backlog.** Link issuance is based on `job.created_at`, not first send. Five capture jobs from October 23 and one purchase job from October 25 are pending, at zero attempts with no frozen body. Their 48-hour reward/confirmation/access links are already expired as of this audit. A first worker call claims up to ten jobs and can send all six to historical recipients. Before any invocation, review permitted recipients and decide an audited skip/recovery/replacement policy that preserves financial evidence. Do not blindly reset/reissue existing jobs or drain the queue as a test. Fresh replacement messages need fresh links and intentional keys, accounting for any prior acceptance.
3. **Correct confirmation-only copy.** A support opt-in can enqueue `capture` with `magnet=false`, but its template still says an exclusive is included. Split or parameterize that copy before testing this message type. No new transactional/marketing blasts are needed.

These changes are planned only in this task. Domain/DNS setup can proceed while they are reviewed. A one-recipient transactional smoke test requires explicit recipient approval and a controlled path that cannot drain the historical queue; no such selector currently exists.

## Needs verification and later hardening

- Exercise frozen-body persistence, stable keys, six attempts, lease reclaim, retries after API acceptance/DB failure, and consent withdrawal using a mocked provider before live email. Existing Edge tests validate worker authorization but never run the actual `runMessaging` send loop. Template existence is not send coverage.
- Welcome/reminder jobs recheck `email_permission` even after queuing or body freezing. Withdrawn permission makes them `skipped` at dispatch. There is still a race between that check and the provider call; a revocation cannot retract an in-flight/accepted email. No database transaction spans Resend.
- Confirmation and unsubscribe require explicit buttons; GET/link-scanner visits do not change permission. An older confirmation token cannot re-enable permission after a later revocation. Unsubscribe does not block transactional recovery/receipts. Body links use a two-step app flow; no `List-Unsubscribe` or one-click header is set.
- `delivery_jobs.status=sent` records API acceptance, not inbox placement. The worker maps provider failures to a generic retry and does not distinguish invalid sender, suppression, rate limit or transient errors, nor honor provider Retry-After. Frozen recipient/sender/language/body remain unchanged on retry.
- No delivered/bounced/complained webhook ingestion or local email suppression table exists. Monitor Resend's events/suppressions before any broader sending. Automated suppression ingestion is needed before campaigns scale. No broadcast infrastructure is implemented.
- A frozen purchase body can survive a later refund; retry skips re-querying purchases. Private redemption still rejects a fully refunded purchase, but email wording could be stale. Add lifecycle coverage before relying on delayed confirmation emails.
- `SUPPORT_EMAIL` is printed in text but is not the Reply-To header. Confirm where actual replies land and add explicit reply routing if required.
- Ordinary retries with an always-running worker are about 31 minutes of total backoff for six failures, plus processing/scheduling. This is not an enforced deadline or inbox SLA. Expired/signing links must be checked on actual recipient devices.

## Owner setup checklist

1. Sign in to the intended Resend team/account. Keep this project and domain distinguishable from unrelated applications; do not create any broadcast or automation.
2. Open **Domains → Add domain**, choose a domain or sending subdomain you control, and select the intended sending region. Resend recommends subdomains for reputation isolation; see [Verified Domains](https://resend.com/docs/dashboard/domains/introduction).
3. At your authoritative DNS provider, copy the exact SPF/return-path and DKIM records displayed for that domain. Preserve existing mail-receiving records and avoid duplicate/conflicting SPF records. Do not guess record names or values.
4. Configure DMARC with the domain operator using a monitored reporting address and a policy appropriate to the actual sending services. Verify SPF/DKIM alignment rather than blindly replacing an existing domain policy.
5. Return to Resend and verify the domain. Wait until the required sending records are verified; keep the dashboard evidence private and redact credentials.
6. Create a named API key with **Sending access**, restricted to this verified domain. Store it privately as `EMAIL_PROVIDER_API_KEY`; never put it in chat, Git or Vite. See [Create API key](https://resend.com/docs/api-reference/api-keys/create-api-key).
7. Select the verified-domain sender and set `EMAIL_FROM_ADDRESS`. Set a monitored `SUPPORT_EMAIL`; verify replies to the From mailbox are also handled because the current adapter has no Reply-To setting.
8. Supply a real business mailing address as `BUSINESS_POSTAL_ADDRESS`. Confirm the approved reachable frontend origin for `PUBLIC_SITE_URL` and matching public endpoint origins. Do not change these during this audit.
9. When separately authorized, set **only** the reviewed email/site secrets in Supabase Dashboard → Edge Functions → Secrets, or a private email-only env file. Do not upload the whole local backend env: it contains unrelated settings and a differing private-file-map digest. Preserve Stripe, signing, storage and worker secrets. Keep scheduling off.
10. After the implementation/backlog gates above and explicit recipient approval, send exactly one fresh transactional test through a controlled worker path. Test the application's adapter, not only the provider's quick-start example. No new payment is necessary: use a fresh permitted reward/recovery request within approved scope.
11. Check the Resend email record, provider ID, sender, recipient, locale, acceptance/delivery events and suppression/bounce status. Confirm app job state matches the provider record without publishing recipient details or private links.
12. Open the actual inbox/spam folder. Verify content, actual From/reply routing, signed download, link expiry/refresh and cross-device origin. Then explicitly test confirmation → one welcome → unsubscribe → queued marketing skipped; verify transactional recovery remains available. API acceptance alone cannot pass these checks.

## Step 6 follows validated Resend delivery

The function is deployed but Supabase currently has no `pg_cron`, no `pg_net`, no `cron` schema and no scheduler Vault entries. `supabase_vault` exists. Every hosted job is still at zero attempts. No external scheduler was observed; its absence cannot be proven from Supabase alone.

After email/consent/retry validation and separate activation approval, configure the guide's one-minute Cron + pg_net + Vault schedule with `SCHEDULER_SECRET`, invoke no more than ten claimed jobs per call, and verify expiration, the one eligible +24-hour reminder per attempt, retry/lease behavior, actual delivery and monitoring. Do not paste secrets into SQL history. Keep unrelated Meta/WhatsApp/live-payment work outside this handoff.
